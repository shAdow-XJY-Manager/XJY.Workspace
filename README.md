## 本地使用

根目录脚本仅依赖 Node.js 标准库，无需安装根目录依赖。Node.js 版本遵循 package.json：`^20.19.0 || >=22.12.0`；使用 pnpm 命令时按 `packageManager` 指定版本运行，也可直接用 `node scripts/…`。

```bash
git clone --recursive https://github.com/shAdow-XJY-Manager/XJY.Workspace.git
cd XJY.Workspace
# 已克隆时恢复超级仓记录的提交；不等同于升级到各仓库远端最新提交。
git submodule update --init --recursive

node scripts/check-workspace.mjs
node scripts/check-readme-sync.mjs
node scripts/submodule-status.mjs
node scripts/check-submodule-health.mjs
```

`check:workspace` 验证配置映射和目录存在；`status`、`health` 检查本地分支、改动和远端跟踪信息，不会刷新远端。`git submodule status` 的 `-` 表示子模块未在超级仓本地配置中初始化，即使目录内另有独立 Git checkout，也应先核对实际 Git 目录和本地更改。不要用批量初始化覆盖现有工作。

## Web 构建与部署

```bash
# 预览明确配置的 Web 产品与跳过原因；不执行 Flutter/npm，不创建输出或更改 docs。
node scripts/build-web.mjs --dry-run
node scripts/build-web.mjs --flutter-only --dry-run

# 指定一个应用，构建到仓库外的目录。
node scripts/build-web.mjs --project pages/shadow-xjy-manager.github.io \
  --output-root /absolute/external/web-builds

# 检查上面的构建结果后，显式重新构建并更新该仓库的 docs。
node scripts/build-web.mjs --project pages/shadow-xjy-manager.github.io \
  --output-root /absolute/external/web-builds --update-docs --cname shadowplusing.cn

# 组件示例仅用于明确指定的验证，不纳入默认产品构建。
node scripts/build-web.mjs --project workspaces/util/core/blurGlass/example --dry-run
node scripts/build-web.test.mjs
```

- 当前验证工具链为 Flutter **3.47.6** / Dart **3.13.5**；各 pubspec 的最低约束为 Dart `>=3.9.2 <4.0.0`、Flutter `>=3.35.0`。升级后的 lock 由较新 SDK 解析；若切换到满足约束的较旧 SDK，先在对应项目重新 `flutter pub get`，不要沿用新 SDK 的解析缓存直接 `--no-pub` 构建。Flutter/pub 仍需由唯一 SDK 执行负责人串行调用。
- 发布用途以根 `package.json.flutterTargets` 为准：`web` 为默认批量 Web 产品，`native` 保留桌面/移动/本地用途，`examples` 仅用于单项目组件验证。标准 web 目录、index 或默认 scaffold 只代表已有平台文件，不能据此授权 Web 发布；未配置的新 Flutter 应用同样跳过。
- 默认公用 Web 产品共 **15 项**：组织门户；novelRead、comicRead、musicListen；gameCenter、world_flutter、findDifferencesGame、flipChess_flutter、parkourGame、rockPaperScissors、snakeGame、ticTacToe、pvz_flutter 这 9 个游戏；websiteTools、customSearchPage。完整运行路径由 `flutterTargets.web` 维护。
- 当前 15 个 Web 产品均保留 Web 平台，原生平台目录已由 Flutter 专用负责人外置归档后收敛：14 个项目的 Android/iOS/Linux/macOS/Windows 共 70 个目录已备份移出，customSearchPage 原本仅有 Web。8 个 native 应用与 3 个 example 保留各自已有平台，4 个库保持原边界；根构建脚本不会创建、删除或迁移平台目录。Flutter/Dart 环境约束以各子仓的 pubspec.yaml 为准。
- **8 个 native 应用**继续按原用途升级验证：tv（Android TV）、backendService（本地服务）、campusPrice/campusprice_flutter（原生客户端）、readingReader/writingWriter（本地工具）、schoolSecondhandApp_flutter（移动应用）、subFontPackage（桌面工具）、fakeBrowser（本地浏览器）。它们即使保留 web scaffold 或旧 partial docs，也不会进入批量 Web 构建；本脚本连显式 `--project` 的 Web 构建也会拒绝。保留原平台目录、旧 docs 与 CNAME，不将升级等同于转 Web。
- native 项目按实际目标分别验证：backendService、subFontPackage、fakeBrowser 的当前 macOS 构建下限为 **macOS 12+**。Android 项目保留 `flutter.minSdkVersion` 动态下限；当前 SDK 对应 API **24**，Trade 的最终候选也预期为 API 24，最终值须核对实际 APK manifest。保留平台、pub get 成功、某一平台构建通过，都不代表全部桌面/移动平台已完成 release 验证。
- blurGlass、clickTextField、listTwoLevel 的 example 仅通过明确 `--project` 才能在现有 Web 平台上验证；不属于公开 Web 产品，拒绝 `--update-docs`。Flutter 库本身跳过。`.metadata`、SDK 依赖、`lib/main.dart`、`web/index.html` 只用于检查类型和运行入口；扫描子仓根及有 pubspec 的一级目录，包括 campusPrice 的嵌套原生应用。
- 配置中的应用缺失或用途重复会报错，避免默默漏构建。构建脚本不自动创建平台、不改 pubspec、不安装依赖；先在对应仓库准备工具链和依赖。
- 组织/用户根站点按 `.gitmodules` 的拥有者和 `<owner>.github.io` 识别，base-href 为 `/`；继承组织站点域名的子项目使用 `/远端仓库名/`。这是 [GitHub Pages 的继承规则](https://docs.github.com/en/pages/configuring-a-custom-domain-for-your-github-pages-site/about-custom-domains-and-github-pages#using-a-custom-domain-across-multiple-repositories)，嵌套应用和示例同样使用所属仓库前缀。不同独立域名才使用 `/`。
- 脚本离线预览按 `docs/CNAME` → 根 `CNAME` → `web/CNAME` 读取文件候选并提示重复/冲突，**文件、README 或仓库 homepage 不能证明当前 Pages 配置**。发布前只读查询 `GET /repos/{owner}/{repo}/pages`，核对 `source.branch`、`source.path`、`cname`、`html_url` 和权限；再按该 source 分支读取 CNAME。门户远端原 README/web 的 `shadowplusing.website` 与实际 Pages/docs 的 `shadowplusing.cn` 不同；即使本地源文件已统一，也不能据此自动切换远端域名；子仓重复域名文件也不能当独立域名已生效。可对单项目使用 `--base-href /确认路径/` 覆盖，或 `--cname DOMAIN` / `--no-cname` 明确候选域名，脚本不会改远端设置。
- 默认输出在 `~/.cache/shadow-xjy-manager/web-builds/`，每次实际构建使用独立目录。`--output-root` 必须位于仓库和仓库祖先目录之外；空格与特殊字符按独立参数传递。脚本直接调用可执行文件，不拼接 shell 命令。
- 所有构建串行执行；`--parallel` 被拒绝。跨会话使用同一 Flutter SDK 时也必须指定唯一执行负责人，避免 SDK 锁竞争。
- 默认构建成功仍不写 docs。`--update-docs` 必须配一个明确的 `--project` 和经远端核对的 `--cname DOMAIN` 或 `--no-cname`；不再自动保留旧 docs/root 或构建带入的 CNAME。选择无独立域名的子项目用 `--no-cname`，门户或确认的独立域名用 `--cname DOMAIN`，此决定同时影响默认 base-href；已审核路径还可用 `--base-href` 指定。构建成功且产生 index.html（Flutter 必须有 main.dart.js）后，才复制至临时目录、保留 `.nojekyll`、应用明确 CNAME 决定再替换 docs。构建/复制失败保留旧 docs；替换失败尝试恢复，恢复失败保留 `.deploy-*` 备份。
- Vue CLI 当前明确跳过：需人工核对 publicPath 和外置输出目录；`build:web:vue` 只报告这一限制，不会宣称完成构建。Vite 使用项目本地可执行文件；CRA 使用项目 build 脚本和 PUBLIC_URL、BUILD_PATH。
- `tech:list` 是根目录技术标记扫描，无法代表嵌套服务或平台能力；Web 产品用途以 `flutterTargets.web` 为准，当前入口可构建性与跳过原因看 `build-web --dry-run`。

更新 docs 是本地部署产物更新，不会 commit、push 或发布；若真实 Pages source 不是当前仓库分支的 `/docs`，应先按审核方案准备正确发布来源，不可把本地替换视为上线。发布前必须检查差异与预览；失败构建产物留在外置输出目录供排查，按需清理。

## 过程资料与运行资产边界

设计文档、概念稿、调研报告、截图、日志和临时验证数据放在仓库外，或仓库内忽略的过程目录：`.local_asset/`、`.local_assets/`、`local_assets/`、`.process/`、`.artifacts/`、`.design/`/`design/`、`concepts/`、`.research/`/`research/`、`.reports/`/`reports/`、`.screenshots/`/`screenshots/`、`.logs/`/`logs/`、`.tmp/`。`.codebase-memory/` 图谱缓存也不进 Git。

根 `.gitignore` 无法控制子仓库的文件；同步规则到每个仓库的实际 Git `info/exclude`：

```bash
node scripts/configure-local-excludes.mjs          # 只预览
node scripts/configure-local-excludes.mjs --apply  # 校验所有 Git 所属目录后应用
node scripts/check-artifacts.mjs                  # 检查新文件，不删除历史文件
```

脚本通过 Git 查询实际 common-dir；共享 worktree 的 exclude 会影响同一仓库的其他 checkout。每次写入前验证目录所有者与 exclude 路径，并保留既有规则；重复应用可更新同一规则块。规则属于本地设置，新 clone 需要重新应用。

README、配置和必要运行说明可以进 Git；新增 BUILD.md、PDF/Office、设计源文件与归档包默认忽略。运行必需的 `assets/`、`fonts/`、`images/`、`static/`、`public/`、`*.xcassets/` 以及 `docs/` 中的部署产物有例外。docs 仅用于站点部署，报告应放过程目录；嵌套过程目录仍忽略，不能借 assets/docs 例外混入。

`check:artifacts` 检查新 staged 文件是否违反 ignore 规则，并拒绝新 staged/未忽略 untracked 中位于运行资源与部署目录外、至少 5 MiB 的文件。大文件按实际运行用途逐项审查，不能凭后缀认定必需。Git ignore 不会取消已有跟踪；根 FLUTTER_WEB_PROJECTS_STATUS.md 属于旧过程报告，不能作为当前部署状态依据；只有 index.html 不能证明 Flutter 部署完整。历史 BUILD.md、大文件与旧报告先审计列举，再单独决定迁移或移除，禁止批量删除。

## 协作与 Git 工作流

开始工作先确认修改范围和实际 `git-dir`。根治理脚本、子仓源码、Flutter 工具链与部署各自明确负责人；同时编辑同一文件或同时调用共享 Flutter SDK 前先协调。Flutter 升级与验证由专用会话串行执行。

子模块通常可能处于 detached HEAD。进入子仓，确认现有改动和分支后再创建 `codex/…` 分支；代码变更在所属仓库审查。根仓库只记录子模块提交指针；子仓提交推送完成且经过审核后，再明确更新根仓指针。不要使用 `git add .` 把过程文件与无关改动一起加入。

```bash
# 只读检查
git status --short
git -C workspaces/game/mini/snakeGame rev-parse --absolute-git-dir
git -C workspaces/game/mini/snakeGame status --short

# 明确决定升级到远端后，再选择目标；这会修改工作树及根仓指针。
git submodule update --remote --merge -- workspaces/game/mini/snakeGame
```

pnpm 的 `update:com/ent/game/learn/sys/util/pages` 与 `update:all` 同样属于修改操作。`push:dry-run` 仅预览推送命令，但仍会查询远端；真正推送必须有明确授权，`push:submodules` 只推当前已提交分支，不会提交工作树。此治理任务不执行 stage、commit 或 push。

新增子仓时同步 `.gitmodules`、`package.json.workspaceGroups` 与上面的导航表，并运行 `check:workspace`、`check:readme`。新增 Flutter 应用还必须明确 `flutterTargets` 的 web/native/examples 用途；已有 web scaffold 不代替用途确认。移除子仓或清理 Git 缓存前先备份已有工作、明确目标；不使用批量强制删除。

`workspaces/sys/crea/mapCreator/` 是未托管的本地 Godot 项目，不计入 47 个子模块。命名约定为 `XJY.<类别>.<可选子类别>.<项目名>`；现有名称以 `.gitmodules` 为准，各仓许可证见所属 LICENSE。

## 可用命令

| pnpm 脚本 | 行为 |
| --- | --- |
| `status` / `health` | 本地子仓状态与健康检查 |
| `check:workspace` / `check:readme` | 配置映射、47 项导航同步检查 |
| `build:web` / `build:web:flutter` | 按明确用途外置串行构建 15 个 Flutter Web 产品，默认不更新部署 |
| `build:web:dry-run` | 预览所有目标与跳过原因 |
| `test:build-web` | Node 回归验证，不执行 Flutter |
| `ignore:preview` / `ignore:apply` | 预览/同步各仓本地过程目录边界 |
| `check:artifacts` | 新文件忽略规则与非运行大文件检查 |
| `validate` | 配置、导航、构建脚本、资料边界、健康检查 |
| `tech:list` / `tech:stats` | 子仓根技术标记列表/统计 |

`validate` 中 health 遇到已有未提交更改或未推送提交会失败，应按现有状态解释，不自动清理工作树。
